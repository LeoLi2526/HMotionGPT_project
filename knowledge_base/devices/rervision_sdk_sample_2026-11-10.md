### 接口不一致需要适配时处理

1. PDF 中 `CamData` 未列实际头文件/Python里的 `devIndex`；`DeviceInfo` 也不同。必须使用配套 DLL/头文件/Python 的一致版本和内存布局；不能只照 PDF 重新声明结构。
2. Python readme 把陀螺仪标作 dps，C++ 示例打印标签却为 1/1000(dps)。缩放存在歧义。先保存SDK返回原值与来源版本，确认后再输出物理单位；加速度说明为除以1000转g，同样需实测核验。
3. readme 个别动态库名称与目录实际文件不一致。目录 V2.2 是资料发布标签，未执行 `SCAM_GetVersion`，不将其冒充已核验的运行库版本。

## 多被试、跨时段采集方案

继续沿用 subject/session/trial。每个设备保留独立原始目录、设备/镜头/固件/SDK版本、时钟采集代、接收端时钟（能取得时）、原始文件校验和及中断日志。相机完整编码画面/原始文件先留存；裁切、转码和去畸变另存，避免丢失元数据区域。

拟新增相机派生表应逐帧保留原文件位置、帧索引、曝光起止原值与解析状态，另表逐条保留IMU原值、采样原时钟、所在帧/槽位和有效性。不能把无效槽位当新样本，也不在缺乏协议时默默去重。上述是适配设计，本轮未实现连续相机记录器。

每次设备重启/时间回退分新时钟段；换被试、重戴、跨日记录新会话信息。各段用有证据的对应事件估计 `t_session = a * t_device + b`，保存拟合点与独立验证点、残差、适用区间。开始/结束都做可重复事件，长记录加中间检查；只有单个起点不能验证漂移。肌电启动与视觉运动可能存在生理延迟，不把动作相关性直接当纯时钟精度。臂环目前仍主要依赖主机接收时间，传输成批到达的不确定性不能被相机SDK消除。
